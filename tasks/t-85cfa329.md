## Description

DEFERRED from P6 (t-063dbcb0) after scoping it against the live 1.3.4 server — a deliberate "not worth it yet", not an oversight.

What exists today: drafts are a whole-list `GET /drafts` read reconciled by diff, on its own 60s interval (SyncEngine.defaultDraftPollInterval), and since P6 a `topic: "drafts"` wake frame forces that read immediately (MailViewModel.handleWakeSignal). So the latency the journal would buy is already ~0, and the only remaining cost is one small list request per minute per account.

What adopting the journal would actually take (more than a day, hence deferred):
- a `listDraftChanges` operation on MailAPIClient + HQBaseAPIClient, plus DraftChange / DraftChangePage DTOs and mapping (the generated op exists in the vendored spec at /api/v1/drafts/changes);
- a per-account DRAFT cursor. `CachedSyncCheckpoint` is keyed per account with one `changeCursor`; drafts need a second, independently bootstrapped one (additive on the rebuildable cache, so no migration — but a new bootstrap/steady-state state machine);
- a drafts equivalent of the whole journal-mode discipline in SyncEngine: checkpoint-before-bootstrap, per-page cursor persist, 404 -> legacy fallback for older servers, and cursor rejection -> re-bootstrap (note the server answers a foreign/out-of-range cursor with 400 INVALID_DRAFT_CHANGE_CURSOR, not 410 — Herald's middleware already maps both to .cursorExpired since P6);
- MailStore.applyDraftChanges (upsert/tombstone) beside the existing reconcileDrafts, plus its tests.

Take it on when drafts stop being a small list — a user with hundreds of server drafts makes the whole-list read expensive, and that is the trigger, not tidiness.
