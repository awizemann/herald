# UI tests for session recovery — plan (2026-09-27)

Goal: automate the screen-level checks of documents/reports/session-recovery-manual-checklist-2026-09-26.md with XCUITest against a fully faked, deterministic app mode, and shrink the manual list to what cannot be faked (real ASWebAuthenticationSession, real https server, hearing VoiceOver). The suite becomes the regression net for the multi-account project.

## Decisions (Alan, 2026-09-27)
- Agents may run UI tests anytime (they take over the real mouse/keyboard).
- Alan approves the one-time macOS Accessibility/Automation prompt on the first run.
- (Default, not asked) UI tests live in their OWN scheme (`HeraldUITests`) so the existing `xcodebuild … -scheme Herald test` stays fast and unchanged.

## Hard constraints
- The test mode is Debug-only (`#if DEBUG`) AND requires an explicit launch argument; Release builds must not contain it (verify with a Release build).
- In test mode NOTHING touches the Keychain, the network, Sparkle, UserNotifications, or analytics: in-memory account store, in-memory SwiftData, in-process fake HQBase (URLProtocol), scripted sign-in presenter, no-op poster/tracker/updater. The release app signed in on this Mac must be unaffected.
- Never contact production; never run build-detached.sh.

## Phases (each: implement → run → fresh-eyes audit → commit on main, no push)

### U1 — Test launch mode (app side, no UI-test target yet)
- `HeraldApp` composition root: when `-HeraldUITest <scenario>` is present (Debug only), build `AppEnvironment` from a `UITestHarness` instead of the real dependencies.
- Fake HQBase (in-process URLProtocol): discovery + registration + token + minimal mail API (mailboxes, conversations/messages, message detail, drafts CRUD, send, signatures list, `/events` refusal → socket stays off). Server state switchable: healthy; **1.4.0 dead session** (refresh 200, new token 401 `invalid_token`); `invalid_grant`; bare 401 on token endpoint; `invalid_client`.
- Scripted sign-in presenter (replaces ASWebAuthenticationSession): succeed / hang until cancelled / fail with error / user-cancel.
- Seeds: `oneAccount` (one https account, a handful of messages), `twoAccounts`, `signedOut` (onboarding).
- Control surface for the tests: a Debug-only hidden "UI Test Controls" command menu (only in test mode) with items to flip server state and presenter behaviour; each item has an accessibility identifier. Also an on-screen, test-mode-only log of requests? — only if needed for assertions like "one send".
- Move/reuse existing fakes (HeraldTests/Support, OAuthTestServer, HeraldKit FakeServer patterns) into a Debug-only app folder rather than duplicating; keep unit tests compiling.
- Tests (unit): mode is inert without the argument; every dependency in test mode is a fake (no Keychain/URLSession.shared); Release configuration builds without the test-mode symbols.

### U2 — UI-test target, identifiers, page objects, smoke
- `project.yml`: `HeraldUITests` (`bundle.ui-testing`, own bundle id, GENERATE_INFOPLIST_FILE), scheme `HeraldUITests`; `xcodegen generate`.
- Accessibility identifiers on: ReauthBanner (message, Sign In, Cancel, reason line), sidebar status slot, compose error bar (message, Sign In, progress), Send, compose body/to/subject, Add Account sheet (field, Sign In, error), sign-out alert, account switcher. No change to labels/VoiceOver text.
- Page objects (Banner, Sidebar, Compose, Onboarding) + launch helper; smoke test: launch `oneAccount`, inbox rows visible.
- `scripts/ui-tests.sh` to run the scheme.

### U3 — Scenarios: dead session + recovery
1. Dead session on Send → banner appears at once; compose shows Sign In; typing doesn't clear it.
2. Automatic attempt (presenter hangs) → banner shows Cancel → Cancel → Sign In returns; Sign In right after Cancel succeeds; banner clears.
3. Sidebar "Sign in again" → signs in; disabled while an attempt runs.
4. Composer keeps its text across sign-in and sends exactly once (fake server send count), double-click Send sends once.

### U4 — Scenarios: failures + guards + accessibility
5. Failed sign-in (presenter fails / invalid_client) → reason line in banner and compose.
6. Add Account activation failure → sheet stays open with the reason.
7. Sign-out failure with two accounts → alert with reason.
8. Add Account for an already-signed-in server → refused inline, no sign-in started.
9. Accessibility: every control above has a non-empty label and is reachable (XCUI element queries).

### U5 — Stabilise + trim manual list
- Run the UI suite 5× consecutively; fix flakes (waits on existence, never sleeps); per-test time limits.
- Rewrite the manual checklist to the remaining manual-only pass (real server, real sign-in window, VoiceOver hearing, callback-scheme/LaunchServices), cross-referencing the automated tests.
- Memory: testing-conventions + build notes (how to run, test-mode rules, identifiers convention).
