Current design (verified at HEAD 177f09f): how Herald detects a dead session, routes it to one re-auth transition per account, lets the user or Herald repair it, and keeps composers alive through it. Policy rules live in [[Automatic Re-auth Policy (frontmost, deferred, rate-limited)]].

## Presentation watchdog & cancel
- [fact] `ASWebAuthenticationSession.start() == true` only means the request reached the out-of-process auth agent; a wedged agent shows no window and never calls back — not a missing resume in our code #aswebauth
- [decision] `WebAuthenticationRunner.authorize` arms its timer only AFTER `start()` succeeds: 45s advisory log (`presentationWarning`) + 10-minute hard `presentationDeadline` → cancel + `.webAuthenticationFailed(presentationTimeoutMessage)`. No "window appeared" signal exists, so the timer also covers a human on the consent page — never shorten it; Cancel is the fast path. Torn down in `finish(_:with:)`, the single resumption point; `onCancel` cancels the ASWebAuthenticationSession. Durations, sleep and a `WebAuthenticationDriving` factory are injected #watchdog
- [decision] Interactive sign-ins are retained (`signInCancellation`) and stamped with `signInGeneration`; `beginInteractiveSignIn` cancels the previous claim. `cancelSignIn()` → `abandonInteractiveSignIn()` bumps the generation and clears `isSigningIn`/`signInStage` itself (an uninterruptible SecItem/agent stall still leaves a usable screen); `cancelInteractiveSignIn()` releases a re-auth's policy claim at once. A stale generation never installs #cancel
- [constraint] Automatic re-auth passes `generation: nil`: never touches `isSigningIn`/`signInStage`/`signInError`/`presentsAddAccount` #auto-reauth
- [decision] Keychain stays a synchronous `nonisolated` `AccountStore` (os_unfair_lock); auth calls go off-main (`AuthCoordinator.offMain`) so the main actor keeps drawing and honours Cancel. `AuthCoordinator.defaultSession` is ephemeral, 15s request / 30s resource, no cache/cookies (`makeSession(...)` seam) — never `URLSession.shared` #keychain #timeouts
- [fact] `addAccount(origin:onStep:)` reports `AuthStep` (discovering…saving); the app maps to `SignInStage` (adds `.activating`) #stages

## Dead-session detection (HeraldKit)
- [decision] `AccountTokenProvider` is the ONE chokepoint. It announces through `setSessionRejectedHandler(_: (@Sendable (SessionDeath) async -> Void)?)`: post-refresh 401 latch (`sessionRejected(token:)`), `invalid_grant` (store cleared; announced by the refresh starter only), `missingRefreshToken`, terminal refusals, and `unknownAccount` from the coordinator's sign-out generation (not latched, grant kept) #dead-session-latch
- [decision] Latch trigger: `AuthenticatingMiddleware` calls `sessionRejected` only when the post-refresh retry is still a 401 with explicit `error="invalid_token"` (`isExplicitInvalidToken`; token or quoted form, case-insensitive). Socket: `MailEventChannelError.unauthorized(invalidToken:)` via `URLSessionMailEventChannel.rejection(status:challenge:)`. A bare 401 still gets one refresh+retry (`isRefreshable`) and sync/socket still ESCALATE it (banner) — only the latch is gated #dead-session-latch
- [invariant] `deadGrant` is keyed to the grant (refresh token, else access token), in memory, set only if `token` is still the STORED access token; then `accessToken()`/`refreshAccessToken` fail fast with `.reauthenticationRequired` (and announce). A different stored grant clears it, so superseded providers (open composers) work after re-auth. Keychain not cleared on a latch #dead-session-latch
- [invariant] Once per grant: `announcedDeath` is recorded BEFORE awaiting the handler (actor re-entrancy); an empty store announces only if nothing was announced since the last live grant; `observe` resets on a different grant; a death found with no handler is not recorded (next request announces). `deadGrant` ≠ `announcedDeath` on purpose #dead-session-hook
- [fact] `SessionDeath{accountID, isCurrent()}` → `isStillDead(grant:)`: stale only when a DIFFERENT grant is stored (empty = dead, unreadable = current), and a rotation this provider MINTED (`rotations` lineage, max 32, adopted grants excluded) is the same death. `deathOfStoredGrant()` = marker for the stored grant, no latch/announce, nil if unreadable #dead-session-hook
- [decision] `OAuthError.isTerminalRefreshRefusal` = `isRejectedClient` (`invalid_client`, `unauthorized_client`) ∪ `isScopeRefusal` (`invalid_scope`, `invalid_target`). Bare token-endpoint 401 (`http_401`) is `isRetryable`, never terminal. On invalid_grant/terminal: adopt a moved-on store (`tokens(replacing:)`), check client-id supersession, then invalid_grant → clear store; terminal → `TerminalRefusal`, latch + announce once, tokens NOT cleared (another process may hold a live grant under a new client) #dead-client
- [invariant] A refresh's outcome is written ONLY over the grant it spent: `AccountStore.setTokens(_:for:ifRefreshTokenIs:)` (compare-and-set on the stored refresh token; empty store never matches). `performRefresh` persists `fresh` through it; if the store moved on (a sign-in here/newer graph/another process, or another rotation) ours is DISCARDED — not revoked (RFC 7009 may revoke the whole authorization, i.e. the winner) — and the stored grant adopted with `mintedHere == false`, so the P9b lineage never links the dead grant to a re-auth. Empty/unreadable store → the fresh token serves this one request, unpersisted (no resurrecting a signed-out account). The `invalid_grant` clear is the same compare-and-clear, adopting a grant written after its check. `KeychainAccountStore` runs the CAS and ALL token reads/writes under its (non-reentrant) lock. Fixed 05eb4ca (found by U1's deadSession140) #race #dead-session-latch
- [decision] `client_id` is read from the account record at REFRESH time (build-time id = fallback) and sent via `TokenRefreshing.refresh(refreshToken:clientID:)`. If the record's id (no fallback) differs from the sent one, the refusal is superseded: retry once (`maxSupersededRetries`), else throw with no verdict #client-id
- [decision] Only explicit server words forget a registration: `isRejectedClient` → `AccountStore.forgetClientID(_:for:)` compare-and-delete of `client.<origin>` with the SENT id. Scope refusals also forget it, evict persisted `discovery.<origin>` and await `discoveryInvalidated` (coordinator `evictDiscovery`, no generation bump) BEFORE announcing, so the next sign-in rediscovers and re-registers #dead-client

- [invariant] A store ERROR on that compare-and-set (after the token endpoint answered 200) is its own do/catch in `performRefresh`, never the generic catch: the spent refresh token is already rotated server-side, and the old path wrapped the Keychain error as `.transport` and looped back to spend it again → family invalidation/logout (audit F1). Now it logs and serves `fresh` unpersisted, and (since 48720a9, next bullet) the provider keeps it in memory until the store takes it. Test `RefreshCompareAndSetTests.aStoreErrorAfterA200DoesNotRespend` (FailingWriteStore + RotatingRefresher: exactly one token request, caller gets `access-1`); mutation-checked. Fixed dff1fed #race #dead-session-latch
- [invariant] F1 residual FIXED (48720a9): the provider keeps an unpersisted refresh in memory as `unpersisted = (spent, fresh)` (set by `refreshTokens` from `RefreshResult.unpersistedOver`; the store-error return is now `mintedHere == true`, so the P9b lineage records it). `accessToken`/`refreshAccessToken` first run `resolveStored`: store holds anything but `spent` (another process rotated, sign-in, sign-out, cleared) → drop it, the store wins; store still holds `spent` → retry the write as CAS against `spent` (success → settled; lost CAS → re-read); write throws again → act on `fresh` from memory: served while its access token is valid (leeway 0), NEVER refreshed (a second rotation could not be recorded either), past expiry → retryable `.transport` with nothing spent. `sessionRejected`/`deathOfStoredGrant`/`isStillDead` look through it (`effective`), so a dead session still latches on the in-memory grant. Tests `RefreshCompareAndSetTests` (persisted on next call without replay; served while the store fails; expired → no refresh; a new stored grant supersedes); mutation-checked (3/4 fail without keeping the tokens) #race #dead-session-latch



## Routing to the UI
- [decision] `activateAccount` wires `setSessionRejectedHandler(sessionDeathHandler())` right after `auth.tokenProvider(for:)`, before the suspension-free `isStillWanted()` → install; `install(tokenProvider:)` only stores it on `AccountGraph.tokens`. REST and socket share the provider #dead-session-hook
- [decision] `reportSessionDeath` routes by ACCOUNT ID: pin `graphs[id]`, await `isCurrent()`, deliver only if the same graph is still installed, store `graph.sessionDeath`, call `mail.reportSessionExpired()`. No graph → no-op (sign-out can't resurrect) #dead-session-hook
- [fact] `MailViewModel.reportSessionExpired()` is the ONE transition into `.needsReauth`; only the transition fires `reauthenticationRequired` → `attemptAutomaticReauthentication` in a Task (never awaited — awaiting `MailEventSocket.stop()` from the handler deadlocks). `requiresReauthentication(_:)` also classifies `OutboxError`/`SignatureManagementError` `.api(.unauthorized)` #dead-session-hook
- [invariant] `.needsReauth` is sticky against non-auth `.failed` and `.finished`; only an install of a fresh graph clears it #banner

## Automatic vs user re-auth
- [decision] `attemptAutomaticReauthentication`: selected account in `.needsReauth` only; probes `healIfSessionRecovered` first; claims via `autoReauth.begin`; stores the task in `automaticReauthTasks` and finishes the policy only if still registered (a stale return after Cancel must not release a newer Sign In claim) #auto-reauth
- [decision] `reauthenticate(accountID:fromComposer:)` (banner, sidebar, composer): `beginUserInitiated`, generation-stamped, cancellable. A re-auth never takes the window (`select: graphs[account.id] == nil`). A different returned account id → `stopGraph` + `forget` the old one #reauth
- [decision] Cancel is shown for EVERY attempt. `cancelReauthentication` dispatches on `signInReauthAccountID` (not `isSigningIn`): user → `abandonInteractiveSignIn()`; automatic → `cancelAutomaticReauthentication` (remove + cancel task, `finish(succeeded:false)` now → cooldown; Sign In still works) #cancel
- [decision] Late consent → `discardAbandonedSignIn`: existing account (`graphs[id] != nil`) → KEEP the grant and re-install `select:false` in its own Task (`isStillWanted = graphs[id] != nil`, so a racing sign-out wins); banner and composer Sign In clear. New account / signed out meanwhile → `auth.signOut` in its own Task (revoke not cancelled). Never sign out an existing account here: it shares the id #cancel
- [gotcha] A cancel in the browser step also cancels the exchange; a late consent writes tokens only if the cancel lands during the Keychain write (`offMain` is uncancellable). Tests gate the store's `add(_:)` #cancel
- [decision] Self-heal: `healIfSessionRecovered` re-installs a `.needsReauth` account (`select:false`, stored record if readable, no window) ONLY when its `sessionDeath` is no longer current. No recorded death (bare 401 escalated) → first probe records `deathOfStoredGrant()`, heals nothing. Skipped without a real provider, while an attempt owns the account, when a probe runs (`healingAccountIDs`), or when `allowsHeal` refuses. `retryAutomaticReauthentication` (activation, selection change) probes non-selected accounts first, then the selected one's attempt #heal
- [fact] Add Account refuses an already-signed-in origin (live or indexed) and an unreadable index before OAuth (`addAccountRefusal`); re-auth bypasses it #reauth

## Compose
- [decision] `ComposeViewModel.fail(_:binding:)` is the one place a server error becomes `.failed`; `requiresSignIn` only if not signed out, `binding == outboxBinding` and `requiresReauthentication`. `signInAffordance` `.none/.available/.inProgress`; Sign In → `reauthenticate(accountID:fromComposer:true)` for the composer's OWN account. After success the user presses Send — no auto-resend #compose-reauth
- [decision] `install` calls `rebindComposeSessions` synchronously after `graphs.updateValue` → `accountSignedIn(outbox:)`: swap outbox, bump `outboxBinding`, clear + announce, reschedule autosave if dirty (not while `.sending`). Draft, server id and `sendAttemptKey` live on the draft #compose-reauth
- [invariant] Dead-session failure is sticky: edits neither clear the bar nor autosave; cleared by rebind or a status change #compose-reauth
- [decision] Server-draft creates are serialized per composer (`isCreatingServerDraft` + waiters, released when the id is adopted): later saves/uploads/Send wait then re-read. Uploads onto a draft without a server id create via `saveDraft` first, then `attach` on the current outbox (skipped if `AttachmentLimits.server` refuses). After a successful save that leaves the draft dirty, autosave reschedules if nothing is pending/in flight (`isAutosavePending`, `savesInFlight`) and not signed-out/requiresSignIn/sending/`isSendInFlight`/pending attachments. `send()` guards `isSendInFlight` before waiting #compose-reauth
- [decision] Sign-out / different-id re-auth → `closeComposeSessions` → `accountSignedOut()`: stops work, Send blocked (`accountSignedOutReason`, instance `sendHelp`), Save Draft announces `accountSignedOutSaveReason`, never rebound; the window keeps its model so text stays copyable #compose-reauth

## Failure reasons & alerts
- [decision] `reauthErrors[Account.ID]` (`reauthError(accountID:)`) is set by a failed user OR automatic re-auth while it still owns the account; never by Cancel/closed window. Cleared on attempt start, cancel, every `install`, sign-out. Re-auth never writes `signInError` #reauth-reason
- [decision] `signInError` is onboarding/Add Account only. `activateAccount -> ActivationOutcome {installed, abandoned, failed}`; `activate` writes nothing. The Add Account sheet closes only on `.installed`; its didSet clears a stale `signInError` on open unless an Add Account attempt runs (`isSigningIn && signInReauthAccountID == nil`) #reauth-reason
- [decision] Sign-out failure with accounts left → `signOutError` alert on `MailWindow` ("Couldn’t finish signing out"); last account → `signInError`. Damaged account index at launch → onboarding with `damagedAccountIndexMessage` (`accountIndexIsDamaged()`) #reauth-reason
- [fact] UI: `BannerView(detail:)` secondary line; `ReauthBanner.stateChangeAnnouncement(...failureAnnouncedElsewhere:) -> String?` (cancel wording wins; nil when the composer announces — `reauthFailureIsAnnouncedByComposer`); banner `cancelledAccountID` resets on account change. Composer shows `signInFailureReason` while `.available` and announces "Sign-in didn’t work: …". Sidebar `SyncStatusLabel.signInAffordance` → "Sign in again" button, no reason #ui #a11y
- [fact] `addAccount` turns `isRejectedClient` (callback after state check, or exchange) into forget + `clientRegistrationRejected`, not retried — except `unauthorized_client` for a client registered by THIS attempt (`registeredNow`): kept, rethrown as `.server("unauthorized_client")` with readable admin-facing prose (177f09f) #dead-client

## Sign-out ordering & forgetting
- [decision] `AppEnvironment.signOut`: `cancelPendingRestore`; cancel (never await) any interactive or automatic attempt for the account; `autoReauth.forget`; clear `reauthErrors`; `stopGraph`; re-select; `auth.signOut`; purge cache only if no graph came back #sign-out
- [decision] `AuthCoordinator.signOut`: check the index is writable; bump the origin's sign-out generation and evict discovery (by origin, `cacheKey`) BEFORE revoking; revoke with the record's client id, re-read and revoke a rotated token too; remove; when no other account uses the origin, also drop persisted `discovery.<origin>` and forget `client.<origin>` #sign-out #discovery-cache

## Known residuals
- [gotcha] Wedged-attempt races (all need the cancel to land during the Keychain write): a late consent after a newer sign-in overwrites and re-installs on its grant (orphan unrevoked refresh token); one returning during a re-sign-in of the same origin can `auth.signOut` the fresh write; one landing between sign-out's revoke and `remove` leaves a locally deleted, unrevoked grant #residual
- [gotcha] HQBase's authorize endpoint shows its own error page for an unknown client (no redirect), so refresh is what normally discovers a dead client; no unauthenticated client-existence probe exists #dead-client
- [gotcha] Heal: a grant another process stores between a bare 401 and the first probe is recorded as the dead one; superseded providers' rotations are not in the lineage (bounded by the heal interval) #heal
- [gotcha] A very fast failed attempt can coalesce `isReauthenticating` so no banner announcement fires; several mail windows each show the sign-out alert; `signInAgainRequested` does not survive a successful re-auth (W12) #residual

- [gotcha] Cross-process the token compare-and-set is read-then-write (the Keychain has no CAS): a sign-in in ANOTHER process landing in the microseconds between the compare and the write can still be overwritten. The old window was a whole token-endpoint round trip #residual #race
