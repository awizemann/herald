## Observations
- [fact] Routes: GET mailboxes; GET messages (filters folder/mailboxId/search — bare array, NO pagination); GET messages/{id} /thread /html /inline/{att}; GET attachments/{id}; POST messages/{id}/{action} action∈read,unread,star,unstar,archive,trash; POST messages/{id}/remote-media/trust; GET conversations (paged via cursor; the v1 spec exposes NO limit param — server-side page size ~50); POST conversations/{id}/{action}; drafts CRUD + POST drafts/{id}/attachments (multipart) ; POST send; POST reply #routes
- [constraint] Bearer tokens are AUDIENCE-BOUND: request `resource={origin}/api/v1` on BOTH the authorize and token calls or the token is rejected (401 INVALID_OAUTH_TOKEN); tokens minted for /mcp or /mcp/full do not work on /api/v1 #oauth
- [fact] OAuth: discovery at /.well-known/oauth-authorization-server (issuer {origin}/api/auth); dynamic client registration allowed unauthenticated (public client, token_endpoint_auth_method none); scopes mail:read mail:write mail:send offline_access; PKCE authorization_code + refresh; device flow also exists (verification at /device) #oauth
- [fact] Scope→route: mail:read = mailboxes/messages/conversations/attachments/html/inline; mail:write = message+conversation actions and remote-media trust; mail:send = ALL drafts routes + send + reply #scopes
- [fact] Errors are `{error:{code,message}}`; 401 carries `WWW-Authenticate: Bearer resource_metadata="{origin}/.well-known/oauth-protected-resource/api/v1", scope="…", error="invalid_token|insufficient_scope"`; server has NO delta/changes endpoint and NO push except browser Web Push (VAPID) → client polls #contract
- [constraint] Minimum supported server is 1.3.4; POST /forward 404s on older servers; no capability negotiation exists #min-server

- [fact] PAGINATION (upstream #35): GET /messages `limit` 1–100 (default 100), opaque versioned `cursor` ("m1"), `Link: <url>; rel="next"` header absent on the last page; 400 INVALID_LIMIT / INVALID_CURSOR #pagination

## Signatures (upstream 1.3.4) — verified 2026-09-04

Verified by reading the 1.3.4 server source (`worker/features/signatures/{routes,service,queries,content,validation}.ts`, `worker/features/send/{routes,service,body,forward}.ts`, `worker/features/drafts/{routes,queries,validation}.ts`, `worker/db/schema-signatures.ts`, `migrations/0021_email_signatures.sql`) plus `api/hqbase-mail-api-v1.openapi.json`. NOT yet exercised against a live server (the local 1.3.4 instance was down).

- `GET /api/v1/signatures?from=<exact address>` (scope `mail:send`) → `{automaticSignatureId: string|null, signatures: Signature[]}`. `from` is REQUIRED; a missing/invalid one is 400 `SIGNATURE_INVALID`, an unknown mailbox 404, no access 403. Only signatures usable from that exact address come back (personal + that mailbox's + that mailbox's domain's). The same routes are mounted under `/api/v1` and `/api/v2`.
- A `Signature` has `scope` ∈ user | mailbox | domain, `scopeId`, `scopeLabel`, `isDefault` (default WITHIN its scope). The AUTOMATIC pick is the mailbox default, else user default, else domain default — reported as `automaticSignatureId`, which is null when the address has none.
- Clients send a SELECTION, never text: `signature: {mode:"automatic"} | {mode:"selected", id} | {mode:"none"}`, accepted on `DraftInput`, `SendInput`, `ReplyInput` and `ForwardInput`. A `selected` id that is not usable from the From address is 400 `SIGNATURE_NOT_AVAILABLE`.
- The SERVER appends the signature to the outgoing message: `assembleMessageBody` joins authored text → signature → quoted context (`worker/features/send/body.ts`), and inline signature images become `cid:` attachments (`prepareSignature`). A client must NEVER concatenate a signature into the body — same invariant class as the quoted original.
- Drafts store a resolved `SignatureSnapshot {mode, id, name, html, text}` (`Draft.signature`, required since 1.3.4). `resolveDraftSignature`: an explicit selection wins; NO selection means "no signature" on create and "keep what is stored" on update — re-resolving to `automatic` when the From address changed, or when the stored selection is no longer usable.
- `resolveSendSignature`: when `draftId` is present the DRAFT's snapshot is used and the body's selection is IGNORED (and a From that disagrees with the draft is 400 `DRAFT_FROM_MISMATCH`). Without a `draftId` the body's selection decides, and an omitted one means no signature. `POST /forward` takes no `draftId` at all, so its selection is always the deciding one.
- `drafts.signature_id` is `ON DELETE SET NULL`, so deleting a signature leaves its drafts with `{"mode":"selected","id":null}`. The server itself degrades that to `automatic` on the next save; clients must tolerate it. This WAS a spec trap: upstream's `Draft` used to be `allOf[DraftInput, {…, signature: SignatureSnapshot}]` with `DraftInput.signature` a SignatureSelection `oneOf`, so one key decoded twice and a null id matched no case. Herald patched its vendored copy to split the response half out as `DraftFields`. **UPSTREAM ADOPTED THE SPLIT AT 1.4.2** (our #113), so since the 2026-09-19 re-vendor there is NOTHING to re-apply after a spec regen — `DraftFields` is upstream's own schema.
- Signature MANAGEMENT (`GET/POST/PATCH/DELETE /api/signatures`, cookie session, sanitised HTML, ≤5 inline images / 256 KB, per-scope unique names and single default) is a WEB-APP surface, not part of the Mail API. Herald consumes signatures only.


## Labels (upstream 1.3.4) — verified 2026-09-04 against the LIVE local 1.3.4 instance

Verified by reading `worker/features/labels/{queries,routes}.ts`, `worker/features/messages/{routes,change-routes,queries,conversation-routes,conversation-queries}.ts`, `worker/features/drafts/{routes,queries,list-queries}.ts`, `worker/auth/{mail-api,auth,oauth-principal}.ts`, AND by exercising `http://localhost:8787` with an owner cookie session (seeded `owner@hqbase.test`).

- **THE LOAD-BEARING FACT: v1 message/conversation/change payloads carry NO `labels` field.** The embed is gated on the base path — `includeLabels(request) { mailApiBasePath(request) !== "/api/v1" }` (messages/routes.ts:325) and the same `=== "/api/v1"` test in conversation-routes.ts and change-routes.ts. Live proof: `GET /api/v1/messages` keys have no `labels`; the identical `GET /api/v2/messages` request returns `labels: [...]`. So on v1 the ONLY way to learn membership is the `labelId` filter.
- **DRAFTS ARE THE EXCEPTION**: `mapDraftRow` always attaches `labels` (drafts/queries.ts, list-queries.ts) with no version gate, so `GET /api/v1/drafts` DOES return them — verified live. Neither OpenAPI document declares `labels` on `Draft` (nor on Message/Conversation), so the generated client cannot see it: same family as the `DraftFields` trap. Reading draft labels needs a vendored-spec patch first.
- **Moving to /api/v2 to get the embed is NOT a drop-in.** Both versions mount the same route tree (`routes/index.ts:91-92`) but an OAuth token is bound to exactly ONE resource: `oauth-principal.ts:90` rejects unless `tokenResources[0] === options.resource`, and the resource is `origin + "/api/v1"` vs `origin + "/api/v2"` (auth.ts:168-172, mail-api.ts:245-249). A v1-consented token gets 401 on v2 — adopting v2 means re-consenting every account.
- `GET /api/v1/labels` (scope `mail:read`) → `Label[]`, `ORDER BY name COLLATE NOCASE, id`. `Label{id,name(1..80),color,createdAt,updatedAt}`; `color` is a CLOSED set of ten: gray, red, orange, amber, green, teal, blue, indigo, purple, pink.
- Labels are SHARED workspace-wide (one `labels` table, no per-user scoping) and organization-only — the route text is explicit that they "never grant mailbox access or change folders". Label CRUD (`POST/PATCH/DELETE /api/labels`) is a WEB-APP surface: cookie session, owner/admin only. Herald can never create or rename one.
- `PUT`/`DELETE /{messages|conversations|drafts}/{id}/labels/{labelId}` → `LabelAssignmentResult{affected, assigned, labelId, labels[], messageId?, threadId?, draftId?}`. Scope is `mail:write` for messages/conversations and **`mail:send` for drafts**. `labels` is the AUTHORITATIVE FULL SET AFTER the write — for a message its own labels, for a conversation the DISTINCT UNION across every accessible message of the thread (`labelsForThreadIds`). That is what lets an optimistic assignment reconcile without a second request.
- The CONVERSATION route takes a MESSAGE id, like the conversation action routes (`setConversationLabel` selects `thread_id` from it under the access predicate, then fans the write out over every accessible message of the thread). `affected: 0` there is NOT the no-op the triage actions must undo — it means every accessible copy was already in the requested state.
- Filters: `labelId` (single) and repeated `labelIds` on `GET /messages`, `/conversations` and `/drafts`. **`labelIds` is an AND**, not an OR — `queries.ts:169-170` appends one `EXISTS` per id. An unknown label id is a 404 on the LIST call (`requireLabel` per id, routes.ts:55), not an empty result.
- `GET /changes` REFUSES `labelId`/`labelIds` (and mailbox/folder/search) with 400 `INVALID_CHANGE_FILTER`.
- **Label-only edits DO reach the message change journal**: `setMessageLabel`/`setConversationLabel` batch the assignment write with `UPDATE messages SET updated_at = ?`, so the journal reports an `upsert` for the message — verified live (assigned a label, the next `/changes?cursor=` page carried the message). But since the v1 upsert payload has no `labels`, the journal says only "something about this message changed". So the journal is NOT a label delta and cannot drive chips.
- Label mutations also publish a workspace mail event (`publishWorkspaceMailEvent(env, "labels")`) — the `topic: "labels"` frame of the `GET /events` wake socket. Herald does not consume that socket yet (P6).


## Events WebSocket (`GET /api/v1/events`) — verified 2026-09-04 against the LIVE local 1.3.4 instance

Verified two ways: by reading the 1.3.4 server source (`worker/features/events/{route,durable-object,service,types}.ts`, `worker/auth/mail-api.ts`) and by holding real sockets open against http://localhost:8787 (raw WebSocket probe + Herald's own `URLSessionMailEventChannels` in a live test).

- [fact] UPGRADE: plain `GET` with `Upgrade: websocket`, authenticated by the ORDINARY `Authorization: Bearer …` header — no token query parameter, no subprotocol (`Sec-WebSocket-Protocol` comes back absent). Same `requireMailApiPrincipal(…, "mail:read")` as REST. A session COOKIE also works when no `Authorization` header is present, and only then is the `Origin` header checked (`validateSessionOrigin`, must equal the server's own origin) — the bearer path skips that check #events-upgrade
- [fact] REJECTIONS are ordinary HTTP responses BEFORE the 101, so a client reads them off `URLSessionWebSocketTask.response`: 401 `UNAUTHENTICATED` with a real `WWW-Authenticate: Bearer resource_metadata=…, scope="mail:read"` challenge (observed live), 403 on scope/origin, 405 non-GET, 426 without the upgrade header, 503 `EVENT_SERVICE_UNAVAILABLE` when the Durable Object binding is missing or unreachable ("Continue with HTTP synchronization") #events-errors
- [fact] FRAMES are exactly `{"type":"changed","topic":"…"}` — no payload, no cursor, no id, no coalescing (two mutations 3s apart produced two frames). Topics are `messages|mailboxes|labels` always, plus `drafts` ONLY when the principal holds `mail:send` (the topic set is chosen at upgrade, `route.ts`) #events-frames
- [fact] TOPIC MAPPING IS NOT WHAT THE NAMES SUGGEST: assigning/removing a LABEL on a message publishes `messages`, not `labels` (verified live — `messages/routes.ts` calls `publishMessageMailEvent`). The `labels` topic fires only for label CRUD (create/rename/delete on the non-v1 admin route, owner/admin only). Since the v1 message payload has no `labels` field, a `messages` frame can never fix label MEMBERSHIP — that still needs the per-label sweep #events-topics
- [fact] LEASE: exactly 10 minutes from upgrade (`connectionLifetimeMs`), enforced by a DO alarm. Observed live: opened 21:04:34.926Z, closed 21:14:34.930Z with close code **1008**, reason "Reconnect to renew authentication." Credential revocation does NOT close a live socket — the lease is the revocation window. Max 3 connections per user (`maxConnectionsPerUser`): a 4th CLOSES THE OLDEST with 1008, so a client that leaks sockets evicts itself; 1000 per workspace, over which the upgrade answers 503 #events-lease
- [fact] The DO auto-responds "pong" to a client TEXT frame "ping" (`setWebSocketAutoResponse`), and CLOSES the socket with 1008 on any OTHER client message ("Client messages are not supported") — a client must never send anything else. Publishes are best-effort: `ignoreMailEventFailure` + `waitUntil`, 3 attempts with 100/200ms backoff, dropped silently on failure. Wake-only means wake-only #events-delivery

## Change journal (`GET /api/v1/changes`) — verified LIVE 2026-09-04 (closes the t-8a1c0051 verification)

- [fact] Checkpoint (no `cursor`) returns `{"changes":[],"nextCursor":"…","hasMore":false}` — exactly the shape `SyncEngine.bootstrap` assumes. A mutation then shows up as ONE `{"type":"upsert","message":{…full MessageSummary…}}` entry at that cursor, `hasMore:false` #changes-live
- [gotcha] A cursor that is malformed, FOREIGN (journal rebuilt, account moved server) or beyond the journal answers **400 `INVALID_CHANGE_CURSOR`**, NOT 410. 410 `CHANGE_CURSOR_EXPIRED` is documented but reserved for a retention policy the server does not have yet. The cursor is PERSISTED in Herald's cache, so a 400 left as a generic error is permanent: every pass fails on it forever. Fixed in P6 — `AuthenticatingMiddleware` maps 400 `INVALID_CHANGE_CURSOR` / `INVALID_DRAFT_CHANGE_CURSOR` and 410 `*_EXPIRED` alike to `.cursorExpired`, which re-bootstraps #cursor-rejection

## Update (2026-09-19 — spec RE-VENDORED @ v1.4.2, U1 landed)

- [fact] The vendored spec is now upstream v1.4.2 (`git -C ~/Developer/hqbase show v1.4.2:api/hqbase-mail-api-v1.openapi.json > HeraldKit/Sources/HeraldAPI/openapi.json`, then `python3 scripts/vendor-openapi.py`). No Herald-local schema patch survives: `DraftFields` is upstream's, and `SignatureSnapshot.id` / `SignatureCandidates.automaticSignatureId` arrive already-Optional through the normal nullable rewrite, so neither changed a DTO #refresh
- [gotcha] `scripts/vendor-openapi.py` now does a SECOND rewrite. `UpdateSignatureInput` is an object with `properties` PLUS a top-level `anyOf:[{required:[name]},{required:[html]},{required:[isDefault]}]` ("at least one of"). swift-openapi-generator 1.7 reads that as three separate schemas, warns each property "only appears in the required list … skipping", and emits three EMPTY structs — the PATCH body would encode as `{}` and every signature edit would 400. The script drops an `anyOf` whose branches carry nothing but `required` when the schema has its own `properties`; the "at least one" rule becomes a client-side guard (`UpdateSignatureInput.isEmpty`). Watch for this shape on any future upstream schema #generator
- [decision] `includeLabels` is a CLIENT-LEVEL option (`HQBaseAPIClient(origin:tokens:session:includeLabels:)`, default false), not a per-call parameter: six operations accept it, there is exactly one production construction site (`AppEnvironment`), and the `MailAPIClient` protocol stays unchanged so no fake grows six parameters. It is sent as `includeLabels=true` and OMITTED when off #labels-v1
- [constraint] `MessageSummary.labels` is `[MailLabel]?`. `nil` = the server said nothing (key absent — old server, or nobody asked) and the cache must be left alone; `[]` = "this message has no labels" and DOES clear it. A `?? []` in the mapping silently wipes every chip against a pre-1.4.2 server. Same rule for the new optional `MessageDetail.replyTo` #labels-v1
- [decision] OAuth scopes are now an EXPLICIT allow-list intersected with what the resource advertises: `OAuthDiscovery.usedAPIScopes` = mail:read, mail:write, mail:send, signatures:manage, plus `offline_access` always. Requesting everything advertised would pull an unknown FUTURE server scope into the consent screen; intersecting down keeps a 1.3.4 server (no `signatures:manage`) from being asked for one it would reject. With NOTHING advertised the fallback stays the conservative pre-1.4.2 `defaultScopes` — no way to tell 1.4.2 from 1.3.4 there #scopes
- [fact] 409 `SEND_KEY_CONFLICT` and 503 `SEND_RECOVERY_UNAVAILABLE`/`SEND_STORAGE_NOT_READY` need no middleware change: they fall through `AuthenticatingMiddleware`'s `default` branch and arrive as `.server(code:message:)` carrying the server's own code, which is what U3 matches on. Asserted in `Upstream142AdoptionTests` #idempotency
