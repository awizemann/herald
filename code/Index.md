# Code Module Guides

Herald is a native macOS mail-triage client split into two targets:

- **HeraldKit** — a macOS/iOS-ready framework containing auth, sync, composition, and API glue.
- **Herald** — the macOS app: views, design tokens, analytics, and notifications.

This folder is *not* a symbol reference (use `memophant code find <Symbol>` or `memophant code outline <file>` for that). Instead, each guide here explains *why* a module is structured the way it is, what's load-bearing vs. scaffolding, and where to start when you need to change it.

## Reading order

Most load-bearing first:

1. **[Sync Engine](Sync-Engine)** — cache architecture, change tracking, and the MailSyncing protocol.
2. **[App Environment](App-Environment)** — account graphs, composition root, and the per-account object graph.
3. **[Authentication](Authentication)** — sign-in, OAuth, account store, and token refresh.
4. **[Views Layer](Views-Layer)** — SwiftUI surface, focus keys, and the three-pane layout.
5. **[Model DTOs](Model-DTOs)** — data contracts: Sendable boundaries between HeraldKit and views.
6. **[API Client](API-Client)** — HTTP transport, middleware, and the autogenerated MailAPIClient.
7. **[Compose and Drafts](Compose-and-Drafts)** — draft composition, send holds, and outbox service.
8. **[Design System](Design-System)** — MailTheme tokens, chip components, and accessibility.
9. **[Analytics and Notifications](Analytics-and-Notifications)** — usage tracking and new-mail alerts.
